# План реализации, объём MVP и риски

Версия 1.0. Оценки ориентировочные, без учёта ожидания доступов и уточнения исходного файла. Фиксированная цена и обязательная дата запуска не определены.

## 1. Демонстрационный MVP для хакатона

Цель — показать связный путь гражданина и техническую реализуемость всех шести функций. Предлагаемый timebox — 48–72 часа для команды 4–5 человек при подготовленных данных и опыте с выбранным стеком. Это ориентир планирования, а не обещание выполнить весь промышленный объём за выходные.

| Возможность | Демонстрационный MVP | Промышленная версия |
|---|---|---|
| Реестр и карта | 30–50 явно синтетических объектов либо разрешённая реальная выборка | Полный согласованный реестр и обновления |
| Карточка | Все исходные поля, неизвестные значения честно обозначены | Модерация, источники, история и реальные организации |
| До/процесс/после | 2–3 датированных набора, рендер помечен, разрешённое тестовое видео/заглушка камеры | Архивные снимки и согласованные камеры подрядчиков |
| Изохроны | Реальный расчёт по доступному пешеходному графу для выбранных объектов | Версионирование сети, все входы, контроль качества и масштабирование |
| Обеспеченность | Демо-агрегаты и воспроизводимая проектная формула | Утверждённые отраслевые нормы и реальные сопоставимые данные |
| Закупки | Проверенные ссылки/ручной набор, отдельно обозначенные демо-контракты | Согласованный автоматический обмен, история и сверка |
| Удовлетворённость | Синтетические оценки, расчёт индекса и подавление малой выборки | Разрешённые обезличенные оценки реальных ответов |
| Жалоба | Категории, точка, подготовка текста и проверенный внешний переход | Виджет или двусторонний API со статусами при наличии доступа |
| Админ-панель | Импорт с preview и публикация выбранной записи | Все роли, аудит, конфликты, откат и мониторинг |

Маркеры, круги доступности и фиктивные подтверждения отправки не заменяют соответствующие функции. Если времени недостаточно, сокращается число демонстрационных объектов и глубина админ-панели, а ограничения фиксируются в отчёте.

## 2. Backlog и зависимости

| Этап | Работы | Зависимости | Критерий выхода |
|---|---|---|---|
| E0. Уточнение | Исходный файл, роли, АМО, статусы, источники, нормы | Представитель заказчика | Протокол решений, маппинг, разрешённая выборка |
| E1. Основа | Репозиторий, схема БД, API реестра, карта/каталог | E0 в части реестра | Карточка и фильтры, повторяемый импорт |
| E2. Медиа и гео | До/процесс/после, входы, изохроны | Подложка, материалы, граф | AT-05/06 на выбранных объектах |
| E3. Аналитика | Обеспеченность, оценки, публикация методик | Границы, мощности, население, оценки | Воспроизводимые AT-07/09 |
| E4. Интеграции | Закупки, камеры, обратная связь | Согласованные каналы и права | AT-08/10 и условно AT-11 |
| E5. Управление | Роли, модерация, аудит, качество | E1 | AT-01/12/13 |
| E6. Подготовка запуска | Нагрузка, доступность, защита, восстановление, инструкции | Все обязательные функции | Протокол приёмки, оператор готов |

Для промышленного проекта ориентир: обследование 1–2 недели; основа и реестр 2–3; медиа/гео/аналитика 3–5; интеграции 2–4; стабилизация и пилот 2–3. Часть работ может идти одновременно, календарный ориентир 10–16 недель после предоставления ключевых доступов. Оценку пересчитать после E0 и технических проб интеграций.

## 3. Роли команды и ответственность

Заказчик/владелец продукта утверждает объём, методики и приёмку. Владелец реестра отвечает за корректность ОКС; владельцы отраслевых данных — за мощности и нормы. Аналитик/геоспециалист задаёт расчёты и геопроверку. Frontend-разработчик отвечает за сценарии интерфейса. Backend-разработчик — за модель и обмен. QA — за протоколы. Инженер эксплуатации/безопасности — за контуры и восстановление. На хакатоне роли могут совмещаться, ответственность сохраняется.

Менторы помогают уточнять отраслевой контекст; их право утверждать юридические/инфраструктурные решения не предполагается без назначения заказчиком.

## 4. Реестр рисков

| Риск | Влияние | Действие и ответственный |
|---|---|---|
| Нет исходного приложения | Неверные поля и объём | Заказчик предоставляет файл; аналитик утверждает маппинг до массового импорта |
| Нет API ЕИС/региональных закупок | Нет автоматической свежести | Владелец интеграции согласует выгрузку; временно ручной импорт со ссылкой |
| Нет ПОС API | Нельзя подтверждать отправку/статусы внутри портала | Владелец интеграции подключает официальную форму; внешняя отправка без ложного статуса |
| Нет архивных снимков/прав на рендеры | Неполный временной слой | Заказчик предоставляет разрешённые материалы; доступные даты показаны честно |
| Неполная дорожная сеть | Ошибочные изохроны | Геоспециалист проверяет входы и эталонные объекты, отключает недостоверные сценарии |
| Нет возрастных/микрорайонных данных | Недостоверный светофор | Аналитик ограничивает разрешение слоя и показывает no_data |
| Нет оценок ответов | Невозможно измерить удовлетворённость | Владелец обращений предоставляет агрегаты; количество обращений не подменяет оценку |
| Переоценка охвата населения по SIM | Искажённый знаменатель | Утвердить тип населения, поправки и ограничения с поставщиком |
| Разглашение через видео/обращения | Нарушение приватности | Оператор разрешает публикацию и утверждает правила доступа до подключения |
| Много зрителей камер | Превышение канала/стоимости | Инженер ограничивает потоки, рассчитывает ёмкость, мониторит нагрузку |
| Изменения границ муниципалитетов | Несопоставимые периоды | Версионировать границы, пересчитывать или отключать прямое сравнение |

## 5. Демонстрационный сценарий

1. Открыть введённые объекты, выбрать муниципалитет и отрасль образования.
2. Открыть карточку, показать исходные поля, источник и неизвестные значения.
3. Перейти на активную стройку, сравнить исторический кадр, ход работ и рендер.
4. Включить изохроны 10/15 минут и объяснить роль входов и препятствий.
5. Включить социальную обеспеченность, раскрыть формулу и прогноз мощности.
6. Показать контракт с типом записи и источником; показать метку устаревания.
7. Открыть удовлетворённость и пример недостаточной выборки.
8. Подготовить сообщение о мусоре и перейти к официальной форме без фиктивной регистрации.
9. В админ-панели показать ошибочную строку импорта и публикацию исправленной редакции.

## 6. Готовность задач

Definition of Ready: есть ID требования, согласованный сценарий, пример данных, известные зависимости и критерии приёмки. Для интеграции дополнительно — документированный способ обмена либо явный demo-режим.

Definition of Done: реализация проверена по связанным AT, обработаны ошибки/пустые данные, соблюдены роли и demo-маркировка, обновлены API и документация, нет незакрытых критических/существенных дефектов. Макет или описание endpoint не считаются завершённой интеграцией.

Бюджет рассчитывается отдельно: труд команды, серверы/хранилище/трафик, картографические лицензии и съёмка, данные операторов, подключение внешних систем, эксплуатация и аудит. Численные цены без коммерческих условий не подставляются.
